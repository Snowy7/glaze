Glaze / proposed build plan / 4 November 2026

A better Windows,
measured.

Make real work faster: dependency installs, repository operations, file handling, and everyday desktop tasks. Use Glaze as the interface for improvements that can also benefit other applications.

Start with a Windows performance lab and one native workspace acceleration experiment. Ship a benefit only after it survives repeatable measurements and correctness checks. Broader system improvements and native shell styling follow as independent features.

Planning document. No benchmarks, migrations, system-setting changes, or application implementation have been performed for this plan. The percentage targets below are proposed acceptance criteria, not measured results or promised speedups.

The opportunity and the unknown

Confirmed

The community benchmark exercises cleanup and cached dependency installation. It contains large differences across software stacks, including Windows versus WSL entries with matching listed hardware. Its submissions also show why Dev Drive should be tested rather than assumed to win. [1]

The current app already has a performance harness, Rust/Win32 integration, a typed Studio frontend, and registry rollback for per-user appearance settings.

Still unproven

How much native Windows overhead is recoverable on our machines, which layer causes it, and whether a transparent acceleration technique can improve unrelated Windows applications.

Theo's examples motivate the workload selection; they do not establish the cause of every Windows slowdown. A faster Linux environment remains a separate result from faster native Windows. [2]

Working scope: investigate current Windows 11 first; detect support for every feature. Keep existing wallpaper and desktop functionality usable independently of the new work.

01
First deliverable

A repeatable Windows performance lab

Extend tools/perf with a separate system-workload command. The existing scenarios measure Glaze's own processes; this command measures real application work and relevant whole-machine activity without restarting the desktop by default.

  • Pin the workload. Use benchmark commit 535aef76843fe52d6336604111708d884110a0e5. Record exact Git, Node, pnpm, Windows build, SSD, filesystem, volume, package-store location, security software, power state, and free space. Use one exact Node/pnpm pair for the initial comparison; test upgrades separately.
  • Measure meaningful tasks. Start with cached dependency installation, generated-file cleanup, checkout/worktree creation, directory enumeration, and git status. Then add one representative project install or incremental build when benchmark execution is explicitly started.
  • Separate conditions. Distinguish native NTFS, native Dev Drive, and WSL-local storage. First compare software choices on the same volume, then compare volumes; changing drives is a hardware confound. A VHDX-backed Dev Drive is its own configuration. A fresh directory is not a cold OS cache.
  • Collect evidence. Record elapsed and process CPU time, file-operation counts where tracing permits, I/O, private memory, file counts, and logical versus allocated storage. Escalate to short ETW/WPA or Defender recordings only for slow cases. Record tracing overhead. [3]
  • Repeat fairly. Warm dependencies, use offline installs with a fixed lockfile and consistent lifecycle-script policy, and preserve equivalent produced contents. Alternate baseline/candidate order for at least five paired runs; report medians, spread, individual runs, and failures. Label first-run measurements separately. Add repetitions only when noise prevents a decision.
Exit condition: a reproducible baseline report and an evidence-backed list of the dominant costs. All cleanup is restricted to a newly created disposable checkout under a verified test root. Never run the benchmark's cleanup commands in the user's repository.
02
Primary performance experiment

Make native development workspaces cheaper

First try reducing work using existing filesystem and tool capabilities. Run each candidate independently before combining successful changes.

ExperimentConcrete implementationWhat would count as success
Dependency importsCompare supported pnpm copy, hard-link, and clone modes with the package store on the same volume. Verify which operation actually happens and preserve lockfile/install semantics.Less creation work and lower install time, without shared mutable dependencies, failed links, or slower subsequent builds.
Native Dev DriveUse an existing test volume or a deliberately created test VHDX. Compare with NTFS and record Defender's actual mode. Explain asynchronous scanning's tradeoff; never silently turn protection off. [4]A repeatable win for the target workload. Keep NTFS when it wins. No conversion or repartitioning of the user's existing volume.
Workspace copiesExplore filesystem-supported copy-on-write copies of prepared workspaces. Keep Git worktree metadata valid; materialize independent metadata where needed. ReFS block cloning is a candidate, not a guarantee. [5]Faster creation and lower allocated storage. Edits, deletes, permissions, native modules, watchers, and cleanup remain isolated and correct.
Toolchain fixesUse traces to identify excessive scans, redundant subprocesses, metadata calls, or an inefficient import fallback. Fix the responsible tool or integrate an upstream improvement where practical.The workload improves with fewer operations. Any benefit requiring a patched tool is explicitly scoped to that tool.

Separate option: offer WSL-local workspaces for Linux-compatible toolchains. Keep both files and the hot-path tools inside WSL; accessing the same project through Windows bridges is a separate test. Label this “Linux workspace,” never “native Windows acceleration.” [6]

Proposed release gate: one native intervention improves the median of two representative workflows by at least 20%, beyond observed run variation, with no repeatable regression over 5% in secondary workflows. Verify on a second Windows machine before recommending it broadly. These thresholds can be revised explicitly after the baseline, not silently relaxed to declare success.

If nothing wins, publish the negative result and the trace evidence. Do not ship a performance switch that has no demonstrated benefit.

03
Broader operating-system improvements

Three small features with practical value

After the lab, choose the first feature based on the machine's measured problem. Each action is independent of wallpaper themes and records exactly what changed.

Startup and background activity

Show startup entries, their owner, launch mechanism, and measured activity. Help the user disable selected unwanted entries through supported controls. Explain existing Windows behavior before introducing a background resource controller. Later, investigate per-app efficiency settings only when traces demonstrate contention; avoid indiscriminate suspension.

Acceptance: selected entries stop auto-launching, restoration recreates the original configuration, and a real sign-in confirms any boot/readiness claim. Measure net foreground benefit, not merely a smaller process list.

Sleep and docking recovery

Read SleepStudy and wake diagnostics to identify likely drain sources; offer supported hibernation configuration as a labeled workaround. Independently, remember window placement by monitor arrangement and restore it after docking or wake. Use stable monitor identities and respect windows the user moved afterward. [7]

Acceptance: repeat the relevant sleep/dock cycle, preserve reachable window positions across DPI changes, and measure overnight drain before claiming a power improvement. Driver and firmware defects remain separately identified.

One place for supported Windows preferences

Start with a short, version-aware set of recommendation, notification, privacy, and update-scheduling preferences. Show current state, effect, and availability. Do not market quieter UI as a filesystem improvement. Respect organization policy and explain settings unavailable on the installed edition. [8]

Settings contract: inspect → show the specific change → apply → verify → undo. Persist these preferences independently of theme lifetime. If another program or the user changes a value afterward, flag a conflict rather than blindly restoring an obsolete value.
04
Independent customization experiment

Restyle real Explorer and the native taskbar

Prove native customization with one narrow Explorer change first, then test native taskbar styling. Existing Windhawk implementations are reference material; inspect their licensing before reusing code. This track can expand beyond the app's present no-injection architecture, but does not establish any filesystem speedup. [9]

  • First prototype: restyle a specific Explorer surface on one recorded Windows build; retain native file operations and accessibility. Record what is supported and what is deliberately outside the prototype.
  • Second prototype: make the real taskbar resemble our floating dock, preserving window grouping, previews, tray, keyboard access, and multi-monitor behavior where supported. Compare its feature coverage and resource use with our custom dock.
  • Decide from the result: keep native and custom modes as alternatives during evaluation. Move toward the native implementation only when its feature coverage and maintenance cost justify it. Arbitrary top-bar layouts and extra panels can remain our own UI.
Exit condition: feature probes, an explicit supported-build list, a disable path outside Explorer, and automatic disabling after repeated shell failures. Validate Explorer restart, sign-out, DPI changes, and recovery before wider use. A title-bar recolor alone does not satisfy the native-restyling experiment.
05
Conditional research

Pursue deeper storage improvements when traces justify them

This is the route toward transparent benefits for unrelated native Windows applications. The first question is which repeated work we can eliminate while preserving file semantics.

  1. User-mode workspace virtualization. Explore lazy materialization with ProjFS when measurements show workspace creation dominates. Test metadata enumeration, file watching, renames, locking, hydration, and offline behavior. Reduced initial copying must not merely move all latency to the first build. [10]
  2. Filesystem driver research. Consider a minifilter or another storage-layer technique only after identifying a specific expensive path that supported controls cannot improve. A filter adds work too; it needs a concrete algorithm and benchmarked advantage. Prototype in a disposable environment before real data. [11]
Research gate: demonstrate a net native-workload improvement, including first access, steady state, cleanup, memory, and storage overhead. Establish write durability, isolation, crash recovery, and interoperation with security/backup software before product integration. Do not weaken security or durability to manufacture a faster comparison.

A replacement filesystem, generic RAM cache, scheduler rewrite, or universal “Linux-speed Windows” claim is outside the first release. Each would need its own evidence and implementation proposal.

The first implementation slice

Build these in order. The later tracks remain proposals until the first reports tell us where to spend effort.

  1. Add the lab command under tools/perf/src/system/, with typed workload definitions, explicit execution, isolated paths, environment capture, and JSON reports under perf/system/. The default desktop benchmark remains separate.
  2. Run the pinned native baseline when benchmark execution is started. Inspect traces for the slowest task. Compare NTFS import strategies first; add Dev Drive and WSL only as separately labeled configurations.
  3. Implement the simplest evidence-backed candidate and repeat paired measurements. If the cost belongs to Git/pnpm rather than Windows storage, target that tool directly.
  4. Add reusable change handling only when needed. Introduce crates/system for actual inspection/apply/verify/undo operations. Reuse the current journal's before-write discipline, but do not force machine settings into its HKCU-only, theme-lifetime model.
  5. Expose a proven feature in Studio. Add a System entry using existing navigation, Tauri API bindings, and UI components. Store measurements and explicit choices; do not invent an overall “PC health” score.

Architecture that stays small

  • On demand first: the lab and settings actions run when requested. Add no permanent service or second WebView solely for this feature. Any later continuous feature must justify its own idle and memory budget.
  • Privilege only for the operation: inspect without elevation where supported; a narrow helper handles a specific machine-level action when required. The renderer does not receive a general elevated command runner.
  • Typed boundaries: inspection facts, candidate operations, applied-change records, and verification results are distinct types. Represent unsupported, blocked by policy, not measured, no improvement, and rollback conflict explicitly.
  • Correctness tests where they matter: test path containment, paired-result calculations, change conflict/rollback behavior, and workspace isolation. Use real workload runs for performance evidence; avoid tests that merely mirror configuration fields.
  • Net benefit: compare stock Windows, Glaze without the feature, and Glaze with it when evaluating shipped features. Include the app and any helper costs. Working-set trimming does not count as releasing committed memory.

First-release definition: a reproducible performance report plus one demonstrated native Windows improvement with clear scope, verification, and recovery. WSL support, native shell mods, and a custom driver are separate milestones.

No calendar estimates yet. The first baseline determines which implementation has enough evidence to estimate. Proposed assumptions: Windows 11 first, native speed as the primary target, no blanket security reductions, no background tuning daemon, and user-controlled workspace migration.
