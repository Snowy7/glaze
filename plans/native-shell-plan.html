mypaper native: the plan

This plan rebuilds the shell fully native, with live Liquid Glass on every surface and near-zero resource use. A council of GPT Sol, Claude Opus and Grok signed it off after six review rounds. Source: plans/council/native-plan.md (v8).

The plan. WebView2 goes everywhere. Three processes stay always on. The engine is the only process with a hardware GPU, and it draws both the wallpaper and all Liquid Glass. The new shell draws the bars, dock, flyouts, menus and widgets in software, at about 40 MB.

Result. Idle CPU drops from 38–87% of a core to about 0.1%. Total RAM drops from about 670 MB to an expected 330–370 MB. Glass on every surface stays live to what is behind it.

From you: one decision is open (below). Everything else is decided, and the build runs in one go, in the order listed.

Open decision D-W: web and app wallpapers. These include Fluids, Vanta Waves, web pages you add, and a Unity game running as the wallpaper. The engine can't draw glass into them, because they render themselves.

Default: delete both kinds, so every wallpaper is engine-drawn and no second capture design gets built. Alternative: keep them, and glass over them uses the same capture path as flyouts, costing a little while it's on screen.

Your decisions this plan is built on

  • Everything native. Minimize CPU, RAM and GPU, at idle and in use.
  • A destructive rebuild. No dual paths, no WebView2 fallback; old code is deleted as each slice lands.
  • Anything may be rebuilt: the shell, the engine, core, Studio and themes.
  • Styles: Liquid Glass is the default, alongside One UI, Solid, Fluent and Mono.
  • Liquid Glass on every surface, live to what is behind it, with adjustable clear↔tinted and blur.
  • Bars float over the wallpaper, like the widgets.
  • Standalone. Restyling the inside of Explorer and Settings is a separate project, after this one.
  • Kept: the panic hotkey and the undo journal.

Two rules

1. One hardware GPU device for the whole product: the engine's

On your machine, any process that opens a hardware GPU device pays 235–246 MB for the graphics driver (docs/engine-notes.md:27-40). So:

  • The shell draws with software Direct2D and DirectWrite into layered windows.
  • Windows' built-in software renderer (WARP) is allowed. A test asserts that no NVIDIA or AMD driver DLL ever loads into the shell.
  • If WARP itself turns out too heavy, a pure-CPU renderer (tiny-skia) takes over.

Found along the way: today's desktop menu creates a hardware render target (menu_ui.rs:126), so core probably loads the whole driver on your first right-click.

2. If nothing changes, nothing is drawn

Each surface redraws only the region that changed. Animation timers run only while something moves. Glass redraws only when the pixels behind that surface change.

  • Deleted: the mypaper-bars and mypaper-widgets processes. Their Rust services (app bars, tray host, window list, media, audio, network, notifications, stats, icons, journal) become one library inside the shell, with the duplicates between them merged.
  • Cut: HTML widgets and the widget SDK. No third-party HTML widget exists, and plugins cover data needs.
  • Crashes: if the shell dies, core restores the taskbar immediately and restarts the shell in ≤300 ms. Core never waits on the shell, so the panic hotkey works even if the shell hangs.

Liquid Glass, live on every surface

Plates: surfaces over the wallpaper

  • Where: the top bar, the dock and the widgets.
  • How: the shell writes each surface's shape into shared memory. The engine draws the glass into its own wallpaper frame: edge refraction, blur, tint and a highlight that follows the light. The shell draws its content on top.
  • Cost: live by construction, and zero over a still wallpaper unless something moves.
  • Moving surfaces: when the dock magnifies or a widget is dragged, the engine redraws only the glass over its last wallpaper frame, so glass stays at most one frame behind, even on a 30 fps wallpaper.
  • Bars keep their reserved screen space, so maximized apps stop at the bar and its glass needs no capture.

Overlays: surfaces over app windows

  • Where: flyouts, the notification center, the launcher, tray overflow, all menus, and a bar while a window is dragged under it.
  • How: the engine puts a click-through glass window, with rounded corners, directly under ours. It feeds that window from one screen capture per monitor, which exists only while something is open.
  • Cost: the capture reports which regions changed. Frames that don't touch the area behind an open surface are skipped, so a video playing elsewhere costs almost nothing.
  • Screenshots: our windows are excluded from the engine's own capture only (SetWindowExclusionList, confirmed by all three reviewers). So they still appear in your screenshots and screen shares.
  • Menus never overlap. Submenus sit flush against their parent.

Wallpapers

Rain-city, its amber and midnight versions, snow-city and snow-forest move from web pages to engine shaders over their photo. Their glass then works everywhere, and each one stops running its own ~100 MB browser. Rain-city goes from about 30% of a core to ≤4% across both screens.

Build order

N0 · Experiments first

1. Software shell: ≤10 MB, 0% CPU over 60 s, ≤1 ms to redraw a full-width bar, and no driver DLL loaded. It also records the first-paint time.

2. Glass overlay:

  • Sits under a moving popup with the right z-order.
  • Keeps our windows out of the capture, while a Snipping Tool screenshot still shows them.
  • No yellow capture border: tries the unpackaged path first, and falls back to a signed sparse package.
  • Clicks reach the popup.
  • Lags ≤1 frame.
  • 0 glass work while only a video elsewhere changes, or only our own windows change.

3. Engine memory with 2 screens and all the glass; this sets the engine target.

N1 · New UI layer and shell, with the desktop menu

Check: a golden-image test matches; opens in ≤25 ms; core loads no Direct2D.

N2 · Top bar, dock and glass, plus the rain-city/snow port

Core starts the shell right after waiting for Explorer. The shell owns the taskbar hide and the journal.

Check: shell and engine targets, golden images and click tests, rain-city ≤4%, glass ≤1 frame behind the dock.

Deletes: the bars web page, the WebView host, the stand-ins, capture, blur, the bridge, the bars process, the old glass scratch memory, its file transport and its spring.

N3 · Flyouts, notification center, launcher, all menus, with live glass

Check: overlay targets, content ≤30 ms, Arabic and CJK typing in the launcher.

N4 · All 17 widgets and edit mode

Check: the whole-product target, no WebView2 anywhere.

Deletes: the widget pages, the HTML widgets, the SDK and the widgets process.

N5 · Engine cleanup

Remove web and app wallpapers (per D-W), the old snapshot pipeline, and the probe of the high-power GPU.

N6 · Styles and materials

Five styles, the material sliders, icon fonts, and Windows settings sync. Check: one switch restyles everything, and the undo round-trip passes.

N7 · Studio native last, can wait

Rebuilt on the same UI layer, so previews are the real renderer. Tauri and pnpm go. ≤60 MB while open.

Given up on purpose

  • Theme CSS, gradients, image, noise and glow fills, neon presets, ambient widget motion, and two of the four launcher layouts.
  • Settings edited on the widget itself (they move to Studio), HTML widgets, and Windows' own backdrop blur.
  • Per D-W's default: the web and app wallpaper kinds, Fluids and Vanta Waves.

Risks

  • Text sharpness: software text on transparent windows uses grayscale smoothing. You compare it side by side in N0.
  • The glass overlay is the biggest unknown, so it is proven in N0 before any port.
  • Typing in other languages through Windows' rich text control is tested in N3.
  • Size: roughly 15k new Rust lines replace about 21k lines of TypeScript, CSS and glue, plus Studio.
